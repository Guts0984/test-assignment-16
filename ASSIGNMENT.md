# Тестовое задание: склад для интернет-магазинов (fulfillment)

Сервис фулфилмента: несколько интернет-магазинов хранят товар на наших складах. Магазин присылает заказы, склад резервирует товар, собирает, упаковывает и отгружает перевозчику. Кладовщики принимают поставки и раскладывают товар по ячейкам, сборщики собирают заказы со сканером, начальник смены следит за потоком и недостачами. Магазины видят остатки и статусы заказов у себя в кабинете и получают уведомления по вебхукам.

Если что-то неоднозначно — решите сами и запишите решение в README. История коммитов — по этапам работы, CI на каждый коммит.

---

## Стек

| Часть | Что использовать |
| --- | --- |
| База | PostgreSQL 16 + Prisma (сырой SQL — где нужны блокировки, ограничения и отчёты). **Источник правды — Postgres** |
| Redis 7 | **BullMQ**: импорт заказов, резервирование, формирование волн сборки, вебхуки магазинам, истечение резервов, ночные задачи. **Адаптер Socket.IO** между копиями `api`. Потеря данных Redis ничего не теряет |
| `apps/api` | Node.js, NestJS: REST + OpenAPI (`@nestjs/swagger`), **Socket.IO** (`@nestjs/websockets`). В `docker compose` работают **две копии** за nginx |
| `apps/worker` | Отдельный процесс NestJS: обработчики BullMQ. Можно запустить несколько копий |
| `apps/web` | Next.js 15 (App Router), React 19. Клиент API **генерируется из OpenAPI**, TanStack Query, React Hook Form, Tailwind |
| `packages/shared` | Zod-схемы ввода, правила резервирования (FEFO), расчёт отгрузочного дня и cutoff, переходы статусов — общие для `api`, `worker` и `web` |
| Тесты | Vitest; интеграционные — на настоящих Postgres и Redis; e2e — Playwright |

## Сценарии

### Магазин (кабинет и API по ключу)

1. Создаёт товары (SKU): название, штрихкод, вес, габариты, учёт партий и срока годности — да/нет.
2. Присылает заказы через API: позиции, адрес, способ доставки (обычная / экспресс), свой номер заказа.
3. Видит остатки по каждому SKU на каждом складе: на полке, в резерве, доступно, в пути между складами.
4. Видит статус каждого заказа и историю; может отменить заказ, пока он не отгружен.
5. Получает вебхуки: смена статуса заказа, изменение доступного остатка.

### Кладовщик

1. Принимает поставку: сканирует товар, вводит количество, партию и срок годности (если учёт включён). Расхождение с заявкой магазина фиксируется.
2. Размещает товар по ячейкам: система предлагает ячейку (та же партия, свободное место), кладовщик сканирует ячейку и подтверждает.
3. Перемещает товар между ячейками и отправляет перемещение на другой склад.

### Сборщик

1. Берёт следующее задание сборки из волны. Видит маршрут по ячейкам в порядке обхода склада.
2. Сканирует ячейку, затем товар; система проверяет, что это нужный товар и нужная партия.
3. Сообщает «в ячейке не хватает» — недостача оформляется, сборка продолжается из другой ячейки, если товар есть.
4. Сдаёт собранное на упаковку. Упаковщик сканирует заказ, система печатает этикетку (PDF).

### Начальник смены

1. Видит поток вживую: заказы по статусам, волны, кто что собирает, заказы под угрозой опоздать к cutoff.
2. Запускает волну вручную, переназначает задания сборки.
3. Назначает и закрывает инвентаризацию ячеек, подтверждает корректировки остатков.
4. Видит отчёт за период: заказы в срок, время от поступления до отгрузки (медиана и 90-й перцентиль), недостачи и корректировки по складам и сотрудникам. Период и фильтры — в URL.

### Администратор

1. Создаёт склады (часовой пояс, рабочие дни, время cutoff перевозчика), зоны и ячейки (вместимость по объёму и весу, порядок обхода).
2. Подключает магазины: API-ключ, адрес вебхука, минимальный остаточный срок годности при отгрузке.
3. Управляет сотрудниками и их ролями на складах.

## Правила

| Что | Правило |
| --- | --- |
| Резерв | заказ резервируется на одном складе: сначала там, где хватает всех позиций, при равенстве — ближайший к адресу; если не хватает нигде — частичный резерв и статус «ждёт товар» |
| Партии | для товаров со сроком годности — FEFO: сначала партия, у которой срок кончается раньше. Партия с остаточным сроком меньше минимума магазина не резервируется |
| Дорезерв | при приёмке товара заказы в статусе «ждёт товар» дорезервируются автоматически: экспресс первыми, затем по времени поступления |
| Волна | собирается каждые 15 минут или сразу при 50 готовых заказах на складе; заказы к ближайшему cutoff и экспресс — в первую очередь |
| Сборка | одна позиция задания не собирается дважды; сканирование чужой ячейки, чужого товара или чужой партии отклоняется |
| Недостача | ячейка уходит на инвентаризацию и закрывается для сборки и размещения; резерв перекидывается на другую ячейку или партию этого склада, если товар есть; если нет — заказ «ждёт товар» |
| Инвентаризация | ячейка заблокирована до закрытия; расхождение больше 5 единиц или больше 10% требует подтверждения начальника смены; каждая корректировка — с причиной и автором |
| Отмена заказа | до сборки — резерв снимается; во время сборки — собранное возвращается на ячейку возврата и раскладывается заново; после отгрузки — нельзя |
| Cutoff | заказ, упакованный до cutoff склада (по местному времени), уходит сегодня; после — в следующий рабочий день склада. Склады — например, `Europe/Kyiv` и `Europe/Warsaw`; переход на летнее время учитывается |
| Перемещение между складами | товар в пути не доступен ни на одном складе; на складе-получателе становится доступен после приёмки |
| Вебхуки | подписаны HMAC; повторы с паузой; изменения остатка по одному SKU присылаются не чаще раза в 5 секунд, в последнем значении; у каждого события растущая версия, магазин может отбросить устаревшее |
| Импорт заказов | один и тот же заказ магазина, присланный повторно (тот же номер), создаётся один раз; повтор с другим содержимым — ошибка |

Статусы заказа: `received`, `awaiting_stock`, `reserved`, `in_wave`, `picking`, `picked`, `packed`, `shipped`, `cancelled`. Таблица переходов (кто и из какого статуса) — в README.

**Журнал движений:** каждое изменение остатка (приёмка, размещение, резерв, снятие резерва, сборка, отгрузка, перемещение, корректировка) — отдельная запись: что, сколько, откуда, куда, кто, когда, по какому документу. Текущий остаток всегда равен сумме журнала.

**Сид:** 2 склада в двух часовых поясах, 5 магазинов, 20 000 SKU (часть — со сроком годности), по 3 000 ячеек на склад, 1 000 000 движений и 200 000 заказов за год. Около 300 заказов в работе (резерв, волны, сборка), часть из них опоздает к сегодняшнему cutoff, если ничего не делать. Логины и API-ключи — в README.

## Заглушка магазина

Отдельный сервис в `docker compose`:

- отправляет заказы в систему: кнопкой на странице (один или пачка из N) и по HTTP — им пользуются тесты;
- принимает вебхуки, проверяет подпись и показывает их на странице с версиями;
- в режиме хаоса (переключатель в `.env`):
  - заказ отправляется дважды, одновременно в обе копии `api`;
  - каждый пятый вебхук получает ответ 500 или таймаут;
  - иногда сразу после заказа приходит его отмена.

## Инварианты

Это главное, что проверяется. Каждый инвариант должен держаться при одновременных запросах, повторах, рестарте процессов и потере Redis, и на каждый нужен тест.

1. **Остаток не уходит в минус и не теряется.** Ни в одной ячейке, ни по одной партии, ни по SKU на складе; текущий остаток всегда равен сумме журнала движений.
2. **Резерв не больше наличия.** 300 одновременных заказов на SKU, которого есть 100 штук, через обе копии `api` и три копии `worker` — зарезервировано ровно 100, остальные «ждут товар»; FEFO соблюдён.
3. **Дорезерв честный.** Приёмка товара при 50 ждущих заказах — резерв получают экспресс и самые ранние, ни один заказ не получает товар дважды.
4. **Позиция собирается один раз.** Два сборщика сканируют одну позицию одновременно — засчитывается один скан; повтор того же скана (двойное нажатие, переотправка после обрыва связи) ничего не меняет.
5. **Отмена во время сборки.** Отмена, пришедшая в момент последнего скана или упаковки, — либо заказ отменён и всё собранное вернулось на ячейку возврата, либо заказ упакован и отмена отклонена; никогда наполовину.
6. **Недостача не ломает поток.** Сборщик сообщает недостачу — ячейка заблокирована, резерв перекинут в той же транзакции, другой сборщик не может взять из этой ячейки.
7. **Инвентаризация не конфликтует со сборкой.** Начало инвентаризации ячейки, в которой прямо сейчас собирают, — либо скан проходит до блокировки и учитывается в подсчёте, либо отклоняется; расхождение считается от правильного остатка.
8. **Импорт заказов идемпотентный.** Один заказ, присланный 10 раз одновременно в обе копии `api`, — один заказ, один резерв.
9. **Вебхуки доставляются.** При ошибках магазина каждое событие доходит после повторов; изменения остатка не приходят в обратном порядке версий; магазин никогда не видит остаток, которого уже нет дольше 5 секунд плюс время повторов.
10. **Фоновые задачи надёжны:**
    - `kill -9` воркера посреди резервирования или формирования волны — после рестарта всё доделано, двойных резервов и двойных волн нет;
    - несколько копий `worker` не выполняют одну задачу дважды;
    - задача, исчерпавшая попытки, видна администратору и запускается повторно вручную.
11. **Потеря Redis ничего не ломает.** После `FLUSHALL` таймеры волн, дорезервы, вебхуки и истечения продолжаются и ничего не выполняется дважды.
12. **Права — на сервере, в каждом эндпоинте и в сокетах:**
    - магазин видит только свои товары, заказы и остатки — и в кабинете, и по API-ключу;
    - сотрудник видит только свои склады;
    - сборщик видит только свои задания;
    - на некорректный ввод — понятная ошибка с кодом, одинаковая по формату во всех эндпоинтах и описанная в OpenAPI; никогда «Internal server error».

Время в задачах (15 минут волны, cutoff, сроки годности, 5 секунд вебхуков) подменяется в тестах.

## Что сдать

- Репозиторий: `apps/api`, `apps/worker`, `apps/web`, `packages/shared`.
- Запуск: `cp .env.example .env && docker compose up --build`.
  - `docker compose`: `postgres`, `redis`, `api` ×2, `nginx`, `worker`, `web`, заглушка магазина.
  - Миграции и сид создаются сами, других ручных шагов нет.
- Swagger на `/docs`; сгенерированный клиент совпадает со схемой — проверка в CI.
- Экран сборщика работает со сканером: сканер — это ввод с клавиатуры с Enter в конце; работа без мыши; ошибка скана — звук и понятное сообщение.
- Панель начальника смены и остатки в кабинете магазина обновляются вживую; время до cutoff считается по часам сервера.
- Формы с ошибками у полей.
- Остатки SKU по складам на сиде — быстрее 200 мс; поиск заказа по номеру, клиенту, SKU — быстрее 300 мс; отчёт за 90 дней — быстрее 1 с.
- e2e:
  - заказ из заглушки магазина → резерв → волна → сборка сканером → упаковка → этикетка → отгрузка → магазин получил вебхуки со статусами;
  - недостача при сборке → ячейка на инвентаризации → заказ собран из другой ячейки;
  - заказ «ждёт товар» → приёмка поставки → заказ зарезервирован → магазин видит новый остаток;
  - заказ упакован после cutoff → перевод часов → уходит в следующий рабочий день склада.
- README:
  - запуск и тесты;
  - как устроен резерв, FEFO и почему остаток не уходит в минус;
  - как защищены скан, отмена и инвентаризация от одновременных действий;
  - как считается cutoff и отгрузочный день, с примером на переходе на летнее время;
  - список фоновых задач: когда ставятся, повторы, защита от дублей, восстановление после потери Redis;
  - как доставляются вебхуки и почему магазин не видит устаревший остаток;
  - таблица статусов заказа;
  - индексы и ограничения в базе;
  - принятые решения.
